## 이번 PR에 포함된 실제 변경

1. **실패를 성공으로 보고하지 않기**: 다음 단계 URL 누락 시 HTTP 424 + `ok:false`, 다음 단계 상태 `WAITING_TRIGGER_URL`.
2. **Work4 완료 게이트**: `DRAFT_SAVED`, `draft_saved === true`, `published === false`를 모두 만족한 실행만 단계 `DONE` 기록.
3. **상태파일 오류 감지**: 상태파일이 없을 때만 최초 빈 상태 허용. 파싱·권한 오류는 로그와 오류로 표면화하여 이력 무음 초기화를 막음.
4. **인증된 상태 확인**: `GET /pipeline/health`는 토큰 인증 후 설정 누락 및 임시 저장 경로 위험을 보고. `GET /pipeline/status?content_id=...`는 기존 방식 유지.
5. **사전 점검 명령**: `node scripts/check_pipeline_config.js`는 비밀값을 출력하지 않고 필수 환경변수 및 상태 파일 경로를 검사. 단, 볼륨·스케줄러가 실제 동작하는지까지는 확인하지 못함.

## 프로덕션 반영 전 검증 (자동 배포 금지)

1. GitHub PR에서 변경 사항 확인 및 구문 검사: `node --check server.js`, `node --check scripts/check_pipeline_config.js`.
2. 예시 안전 검사: `WORK2_TRIGGER_URL=https://example.invalid/work2 WORK3_TRIGGER_URL=https://example.invalid/work3 PIPELINE_STATE_FILE=/data/naver-work-pipeline-state.json node scripts/check_pipeline_config.js` — 이 예시는 **형식 검사만 통과**, 실제 동작 주소가 아닙니다.
3. Railway에서 실제 Work2/Work3 엔드포인트와 인증 방식을 확인하고 **실제 주소**를 변수로 설정. 서비스가 존재하지 않으면 환경변수만으로 자동화는 완성되지 않습니다.
4. 상태 파일을 유지할 볼륨을 연결. **빈 볼륨을 기존 데이터 경로에 장착하면 그 경로가 가려질 수 있으므로** 먼저 데이터 보존 계획 수립.
5. `GET /pipeline/health` 에 토큰을 넣어 조회. 누락이 있으면 503; **HTTP 200도 E2E 성공 증명은 아님**.
6. 시험 콘텐츠 1건을 기획부터 임시저장/재열기 검증까지 실행. 저장이 불확실한 경우 자동 재시도보다 조회/검증을 우선.
7. 성공 확인 시에만 다음 번호로 전진. 기존 발행·완료분 재업로드 금지.

## 실패 대응 및 롤백

- 팝업 오류: 당시 화면·HTML·콘텐츠 ID를 보관하고 임시저장 목록 확인 뒤 제한적으로 재시도합니다.
- CDP/Relay 오류: 브라우저 로그인과 탭 상태를 확인. 실패 직후 업로드를 다시 시작하지 않습니다.
- 다음 단계 트리거 누락: `WAITING_TRIGGER_URL`을 미완료로 분류하고 실제 Work 서비스 URL을 먼저 연결합니다.
